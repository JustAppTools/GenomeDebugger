Comparator 0.6.7 treats supported compound consequence terms as unordered regardless of semicolon, ampersand, or comma separators; original supplied strings remain in the input record. Comparator 0.6.6 and historical assertion layouts remain archived for verification. Restore reconstructs saved-test assertions and validates required database constraints; hashes and replay still do not authenticate an external source's author.

Application 0.8.2 compares complete imported tabular collections independently of display anchors. Adding a transcript/variant is represented as a row addition, without inferring a selected transcript. Collection identity covers all represented keys and supplied contexts. A consistent copy of the existing workspace passed this validation without rewriting its saved scientific JSON. Readable reports now include unchanged as well as changed represented output rows. These changes add no normalization, cross-assembly mapping, external source authentication, or clinical interpretation.

## Verified behavior

- Input validation rejects invalid bases, unchanged alleles, malformed nested fields, duplicate row keys, and reference alleles that contradict supplied context. Guided input edits primary and additional variants and annotations.
- The pure comparison engine establishes local representation equivalence for equal-length substitution edits on identical declared assembly, accession, and supplied reference context. All length-changing edits, including complex replacements, remain unresolved using supplied context alone. This engine is not a full normalizer.
- An explicit independent NCBI check validates the complete submitted reference allele against pinned GRCh38.p14 primary nuclear RefSeq sequence, then compares contextual SPDI and captures genomic HGVS. Reference mismatch skips notation requests. Observations, URLs, hashes, and flags are reconstructed during bundle verification. The check stays separate from the immutable local-context result.
- Browser comparisons bind the exact displayed NCBI and SnpEff check IDs, or explicitly exclude them. Reports classify current/historical sources using preserved records. Contradictory origin flags and duplicate SnpEff INFO tags are rejected. Mitochondrial targets are rejected before transmission and in replay; saved allele checks are replayed before cache-only use.
- Synthetic inputs are excluded from public-reference allele checks during live fetching, offline replay, bundle verification, and cache validation. Sources and checks are ordered by normalized UTC time without changing immutable provenance. Invalid new timestamps are rejected; malformed legacy dates remain readable after valid dates.
- The captured public example in `fixtures/ncbi-repeat-deletion-observation.json` was fetched live during 0.6.0 development: chr1:10004 CC>C and chr1:10005 CC>C both yielded `NC_000001.11:10003:CCC:CC` and `NC_000001.11:g.10006del`. Annotation placeholders make no consequence claim. Service behavior can change; replay uses saved responses.
- Additional variants match exact assembly/accession/position/ref/alt representations. Annotation matching uses tuples and escaped display paths; delimiter characters cannot collapse separate rows. Switching the primary transcript inside an unchanged full annotation set creates selection changes without false missing-row differences.
- Synthetic transcript replay holds allele, software, release, and configuration constant before attributing selection changes as verified within that supplied fixture. Demo gene/transcript/protein names are fabricated.
- Clinical classifications are compared only within matching condition IDs and frameworks. The app infers no clinical classification.
- Candidate regression checks assert absolute primary and additional outputs, including annotation and variant records. Shared changes in both snapshots fail; row order alone does not. Pinned replay compares output and evidence. Evidence drift is separately visible for candidate runs.
- Current Ensembl GRCh38 SNV retrieval validates query, reference base, and VEP response; captures release/assembly metadata, URLs, response hashes, and retrieval time. The chr1:6524705 C>T and rs56116432 chr9:133256042 C>A examples were checked live against Ensembl and the earlier independent NCBI SNV check. Representation agreement does not validate transcript predictions.
- Local SnpEff execution verifies observed Java, JAR, configuration, and transcript-database file hashes before and after running. It preserves input/output VCF, stderr, command, version, and artifact provenance. A live run of SnpEff 5.4c with `GRCh38.mane.1.0.ensembl` against the preserved chr1 example is in `fixtures/snpeff-mane-public-run.json`. Exact transcript versions did not match, so the comparison remains unresolved. User-supplied VCF remains supported with declared provenance.
- Historical VEP import preserves original JSON bytes and declared original time, software version, release, assembly accession, and source location. Comparisons may select two separately preserved outputs. Historical imports cannot satisfy current API cache lookups. Bundle verification reconstructs parsed observations from original artifacts.
- Portable bundles verify hashes, derive NCBI observations and flags again, and replay declared engine output. Current exports use versioned result IDs; originals remain unchanged. Archived 0.5.0 bundles use frozen 0.5.0 verification rules and remain visibly historical. Hashes detect corruption and contradiction; they do not authenticate uploader or source.

Unit, API, and browser tests cover malformed input, disagreement, offline behavior, tampering, and large bundle round trips.

## Unsupported claims and remaining scope

- Cross-assembly liftover, cross-sequence mapping, mitochondrial HGVS, VRS computation, general HGVS parsing, and symbolic/structural variants are unsupported. NCBI checking covers short A/C/G/T primary variants on pinned GRCh38.p14 primary nuclear sequences. Extra variant rows still match exact representations.
- NCBI contextualization is an observed service result. Preserved responses allow offline consistency checks; internal hashes are not signatures. User reference contexts and arbitrary provenance are not externally authenticated.
- A real second annotation run locates agreement or disagreement but does not establish why an earlier consequence changed. Transcript versions are never silently stripped. No verified biological causal explanation is claimed from a partial match.
- Current Ensembl cannot supply an earlier analysis. Its metadata and VEP calls are not atomic and VEP executable version is not reported. Imported historical metadata is declared. Output comparison reconstruction is supported; reproducing an old pipeline still needs its original executables, databases, configuration, and references.
- Bundled execution records preserve provenance but are not authenticated remote execution attestations. Supplied SnpEff versions or database hashes do not prove execution. The installer records observed SnpEff archive hashes; its latest-distribution URL is mutable.
- Regression runs rerun the local comparator. They do not automatically execute VEP, NCBI, or SnpEff. Explicit adapter and runner actions have their own preserved records.
- There is no ClinVar adapter, authenticated release timeline, patient-specific interpretation, pathogenicity prediction, or clinical review-status inference. More independently sourced cases and performance validation are needed before broader deployment.

GenomeDebugger is a research and bioinformatics quality-assurance tool, not a certified clinical diagnostic device.

## 0.6.5 corrections

Application 0.7.10 requires complete typed SPDI and genomic HGVS observations for the source SNV check. Missing notation data enters provider failure and may use a replay-validated cached check. Invalid older cache entries remain stored and are skipped for reuse. SnpEff evidence admitted with a custom output must still apply to its selected and additional primary-variant gene/transcript/consequence rows. Protein and clinical edits remain outside that check's term-comparison scope. Execution admission validates timing, command text, and fingerprint formats without asserting external authenticity. Long release lists stay intact in source records; bounded provenance summaries keep captures comparable. New submissions reject boolean coordinates and whitespace-only required text. Empty and missing display values are distinct, with the comparison engine unchanged at 0.6.5.

Application 0.7.9 additionally validates assembly claims inside each source record before bundle admission, snapshot conversion, or cache use. Supported names are GRCh38 and its patch releases, paired with a syntactically versioned GenBank/RefSeq accession and a preserved VEP response reporting GRCh38. This does not authenticate the provider or verify a patch-to-accession mapping. Invalid cached metadata is retained for inspection but excluded from fallback. New SnpEff executions retain exact valid UTF-8 stdout/stderr bytes and fingerprints, including CRLF, and reject malformed encoding. Legacy execution records keep their earlier text representation and are labeled accordingly. Provider/artifact JSON nesting is bounded at 64 containers; malformed responses follow ordinary error/fallback paths. Comparator rules remain 0.6.5.

Unordered consequence semantics apply to annotation outputs; arbitrary configuration strings remain exact comparisons. Generic findings link to their affected differences, including additional transcript outputs. Frozen 0.6.4 rules preserve replay of valid older results while current replays receive separate IDs.

Direct source-derived VEP snapshots must agree with the preserved assembly, capture time, artifact hash, and declared generation time when those duplicate fields are supplied. Omitted legacy duplicates remain accepted. This checks internal consistency and does not authenticate the original supplier. Explicit custom candidates retain the source as an input citation and identify their own tool; they do not claim to be unmodified captured VEP output. The candidate form detaches SnpEff evidence against the original output and retains applicable allele reference evidence.

Historical and current admission rejects transcript sets or annotation fields that cannot be represented by the comparison schema, without silently omitting rows. Parsed JSON rejects non-finite and overflowing numeric values. Valid finite numeric metadata survives portable download/import as original JSON text, avoiding JavaScript numeric coercion before hash verification. Malformed NCBI JSON is a provider error and can use the existing cached-after-error workflow. None of these repairs establishes a new biological or clinical claim.


## Application 0.8.0 presentation and import boundaries

The comparator remains 0.6.5. Plain-language explanations are deterministic descriptions of recorded changes and existing findings, not a new causal inference or clinical classifier. Literal DNA diagrams show only edits to supplied reference text. A transcript schematic is explicitly conceptual.

Tabular v1 import preserves original UTF-8 text and declared tool/source metadata; hashes preserve supplied content, not authenticity. It rejects malformed/unsupported rows rather than dropping them. Additional variants retain exact-representation matching. The new identifier resolver only previews explicitly reported forward-strand GRCh38 single-base choices from current Ensembl responses; it neither establishes cross-assembly equivalence nor independently verifies a reference. The selected query must still be captured through the existing source adapter.

No new assembly, VRS normalization, historical authenticity, or clinical interpretation claim is made. Synthetic matching/uncertain examples, scoped adapter tests, and existing public reference fixtures test behavior within the documented limits. Representative-user and assistive-technology sessions remain necessary; automated interface checks do not establish scientific or complete accessibility validation.
